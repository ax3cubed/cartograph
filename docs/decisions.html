One binary indexes, stores, answers, serves the app and speaks MCP. Every reader goes through one query layer, so the app, the CLI, MCP and Ask can't drift apart. Nothing listens beyond 127.0.0.1, and nothing leaves the machine except a call to the model provider you configure.

A · Shape and runtime

X1 · PRODUCT.md open decision
A1

One Rust binary does everything, and the app reads the index through it

cartograph open starts a Rust server on 127.0.0.1 with a random port. It serves the Next.js app as a static export built into the binary, plus a read-only JSON API. The CLI and MCP call the same query code in-process. This closes X1 and the open decision in PRODUCT.md.

Why: the SQL lives in one place. A 412 MB index can't go into the browser: SQLite in WebAssembly would copy it into browser storage and couldn't see live updates. Release is a single file with no Node runtime.

Precedent: Datasette, Jaeger all-in-one (a UI built into a Go binary), zoekt-webserver. Rejected: SQLite in WebAssembly; Electron or Tauri as the default, which add signing and packaging per OS; keeping next start, which needs a second runtime and a second SQLite driver.

A2

The app's server routes move into Rust

A static export can't keep Route Handlers that read the request, rewrites, cookies or dynamic routes without generateStaticParams. So app/api moves into the Rust API, pages fetch on the client, and view state lives in the URL hash (#t=2019-04&lod=module&focus=…). This is the real cost of A1, so plan it as part of stage 3.

Source: node_modules/next/dist/docs/01-app/02-guides/static-exports.md, Unsupported Features.

A3

The local server is locked to this machine and this session

It binds only to loopback and refuses any other address. It checks the Host header against DNS rebinding, and refuses any Origin that isn't its own. The browser URL carries a random token for the session. CORS is never opened to a hosted site.

Precedent: MCP security best practices. Rejected: GitNexus's pattern of letting a hosted front end call localhost, which breaks local only.

A4

The CLI and app versions can't drift apart

They ship in the same binary, so "which CLI goes with app 0.4.0" stops being a question: they're the same version. /api/version exists only for diagnostics.

B · The index

X3 · X5 · X6 · X10 · X12
B1

Everything Cartograph keeps lives in ~/.cartograph, not the workspace folderchanges spec

One folder on every platform: ~/.cartograph/registry.toml, config.toml (providers and preferences; keys stay in the OS keychain), cache/facts.db (the shared parse cache) and workspaces/<id>/ (index.cartograph, ask.db, logs/, reports/, the lock). CARTOGRAPH_HOME moves the whole folder. On Linux an explicitly set XDG_DATA_HOME is honoured instead. On Windows it's %USERPROFILE%\.cartograph. The folder is marked as excluded from Time Machine, because indexes are large and can be rebuilt. Revised 22 Nov 2026 from per-platform data folders: one place to inspect, back up or delete beats following each OS's convention. index_path in config overrides it. A path inside iCloud Drive, Dropbox, OneDrive or Google Drive is refused, with the reason.

Why: SQLite's WAL mode needs its -wal and -shm files on one host. Sync clients upload them separately and can restore copies that don't match, which corrupts the file. I chose the data folder over the cache folder the research suggested, because macOS can empty caches when the disk is low, and a first index can take 40 minutes to rebuild.

Precedent: sqlite.org/wal, How to corrupt an SQLite file. Rejected: an index in the workspace folder, which is often inside a synced Documents folder.

B2

WAL with snapshot reads, one writer, and a real OS lock

Readers keep reading the version they started on while a sync writes. The writer commits a batch per repo or per N commits, then truncates the WAL at the end of the run. A sync takes an OS advisory lock (fd-lock), which the kernel releases if the process dies, so the lock can't go stale. Only a full rebuild or a schema migration writes a new file and renames it into place. This closes X5.

Rejected: copying and renaming on every sync, which is 412 MB of I/O, and Windows can't rename over a file that's open. PID-file locks, whose stale-lock guessing is a classic source of bugs.

B3

Every file format carries a version, and the rules are written down

Index: SQLite application_id (a Cartograph magic number) and user_version, plus a meta table holding format_version, min_reader_version, writer_version and each extractor's version. If the index is newer and still readable, this CLI opens it read-only. If it's newer and not readable, the error says to upgrade. If it's older, the CLI migrates it, or rebuilds it when no migration exists, since the index is a cache.

cartograph.yaml and the override file: a required version: 1, plus a JSON Schema generated from the Rust types with schemars. The schema ships on disk and is linked through the yaml-language-server comment, so editors validate it offline. This closes X6.

Precedent: rusqlite_migration (user_version), Cargo.lock's version, Terraform state's version and lineage.

B4

Compare indexes by a hash of their facts, not their bytes

The same commits produce the same fact hash: SHA-256 over a sorted, canonical list of facts and intervals, with row ids and timestamps left out. It's stored in meta, and cartograph verify compares two indexes, or an index against a manifest. This answers X12.

Why: a SQLite file's bytes depend on page size, the SQLite version, the freelist and the insert order. SQLite's own dbhash tool uses the same idea.

Precedent: sqlite.org/dbhash. Rejected: byte-identical files.

B5

One branch per repo, with branch overlays on demand

The timeline is the first-parent history of each repo's default branch. A branch or PR is an overlay: a branch row (repo, ref, base commit, head commit) plus intervals tagged with that branch's id, for the commits between the merge base and the branch head. A query for a branch reads main as of the base commit, and the overlay rows win. Facts are cached by blob id, so an overlay costs about the size of its diff. Overlays are created for the checked-out branch and for cartograph impact <ref>, and dropped once the branch is merged or deleted. This closes X3 and the open question about branches.

Precedent: zoekt stores each blob once with a bitmask of the branches it's on. Rejected: indexing every branch fully, and GitNexus's full copy of the index per branch.

B6

Every derived row records what it was built from

Each derived row stores an inputs_key: a hash of its input blob ids or upstream fact hashes, the extractor name and version, a config hash, and for AI output the model id and prompt version. A run recomputes the keys and rebuilds only the rows whose key changed. AI output is marked stale instead of deleted. Extractors are versioned one by one, so a release doesn't invalidate everything. This closes X10.

Precedent: Bazel action keys, Salsa in rust-analyzer, Glean's derived predicates. Rejected: one cache version for the whole package, which is what GitNexus does.

B7

Read git with gitoxide; replay from the merge base after a rewritebenchmark

gix handles object reads, walking history and diffing trees. Rename detection runs per first-parent commit: exact blob matches first, which costs almost nothing given the cache, then gix-diff's similarity matching (50%, at most 1,000 candidates), with a note on the commit whenever the limit is hit. If the last indexed commit is no longer an ancestor of the branch, Cartograph finds the merge base, reopens the intervals opened after it and replays from there. It falls back to the git command only for partial clones.

Precedent: Cargo, jj and GitButler all use gix. gix-diff docs. Rejected: libgit2, which is C with a GPL-plus-exception licence; and parsing git log -M. Before code: benchmark rename detection on remotion against libgit2.

C · Discovering the workspace

.code-workspace · registry · services
C1

Read .code-workspace exactly as VS Code does

Parse it with the jsonc-parser crate, which allows comments and trailing commas. Resolve folders[].path against the folder holding the workspace file; an absolute path is used as it is. ~ and ${env:…} stay literal, because VS Code doesn't expand them, and doctor warns about them. A uri is accepted only if it's file:. If remoteAuthority is set, the whole file is skipped. name falls back to the folder's name, and duplicate folders are removed.

Precedent: VS Code workspaces.ts, toWorkspaceFolders and resolvePath. Rejected: json5, which is a different grammar, and serde_jsonc, which is unmaintained.

C2

With no workspace file, walk three levels and stop at each repo

The ignore crate's walker respects .gitignore, and the depth is 3. It stops going down a branch at the first .git, never follows symlinks, and always skips node_modules, target and .venv. Submodules belong to their parent repo unless the workspace file lists them. Worktrees are grouped by --git-common-dir. Shallow clones are flagged, and bare repos are skipped.

C3

How the default branch is found, in order, without the network

1. default_branch in cartograph.yaml. 2. origin/HEAD. 3. init.defaultBranch, if that branch exists. 4. main, then master. 5. The current branch, with a warning. It never runs git remote show, which contacts the remote. Since Git 2.48, a fetch fills in a missing origin/HEAD, so sync --fetch fixes that case on its own.

Precedent: git-town's commands.go, Git 2.48 release notes.

C4

A per-user registry at ~/.cartograph/registry.toml

Entries are keyed by the repo's canonical path, with its remote URL and root commit stored too, so a clone that moves can be matched again. It's written under a lock to a temp file, then renamed into place. If two folders hold clones of the same repo, Cartograph warns.

Precedent: direnv's allow list, gh's and mise's use of ~/.config, GitNexus's sibling-clone warning. Rejected: keying by remote URL, because forks share URLs and repos without a remote have none.

C5

cartograph.yaml is committed next to the workspace file

If that folder isn't a repo, init says so and suggests the usual fix: keep acme.code-workspace and cartograph.yaml in one of the repos, or in a small workspace repo, with ../ paths to the others. Then teammates can share the map by committing one file.

C6

How a monorepo is split into services, first match wins

1. Entries in cartograph.yaml. 2. Backstage catalog-info.yaml components. 3. Workspace manifests: pnpm, npm, go.work, Nx project.json, Cargo, Composer. 4. Something deployable turns a package into a service rather than a library: a Dockerfile, a compose build, the source behind a k8s Deployment, a Procfile, serverless config. 5. Otherwise the whole repo is one service. Compose and k8s service names become host aliases, so http://orders:8080 resolves to the orders service.

Precedent: Backstage catalog model, Nx project graph. Rejected: guessing from folder names like services/*, and running build tools, which need a toolchain and the network.

C7

"Split" on board S4 writes to the manifest

It adds a services: entry to cartograph.yaml, the first rule in C6, shows the diff, and re-indexes only that repo.

D · Keeping the index current

open question 1 · board S3
D1

Answer now, refresh in the backgroundchanges spec

Every read (the CLI, MCP, the app) runs a cheap check: each repo's HEAD against its indexed commit. That takes under 100 ms and doesn't touch the network. If a repo is behind, the read answers from the current index straight away and says how many commits behind it is. Then it starts an incremental sync in the background if none is running. The next read is current. auto_sync = "background" | "never" in config, default background. A command that needs a current answer, such as impact in CI, takes --wait.

Why: the research disagreed with itself. The CLI research wanted reads to block on a sync; the MCP research wanted reads only to report stale data. A sync that blocks can run past agent tool timeouts (Claude Code moves calls longer than about 2 minutes to the background, and the TS SDK client gives up after about 60 s). Only reporting it leaves the index behind forever unless something else runs. Answering now and refreshing in the background gets the speed of the second with the freshness of the first, and needs no hooks or daemon to be correct.

Precedent: HTTP's stale-while-revalidate, and GitNexus's "N commits behind" hint. Rejected: blocking reads, and reads that only report.

D2

Only one sync at a time; a second request marks it dirty

A sync that finds the lock held sets a "dirty" flag and exits with code 0. The sync that's running checks the flag before it finishes and runs one more round if it's set. So hooks, background refreshes and agents can all ask for a sync without piling up. This replaces exit code 4.

D3

Hooks are optional, and installed the way git now prefers

On Git 2.54 and later, hooks go in config: hook.cartograph.command plus a hook.cartograph.event for post-commit, post-merge, post-checkout and post-rewrite. These run alongside any other hooks. On older git, Cartograph finds the hooks folder with git rev-parse --git-path hooks, which respects core.hooksPath. It creates the hook if there isn't one, or appends a marked block to an existing shell hook, and otherwise refuses and prints the line to add. If husky or lefthook owns the hooks, it writes nothing and prints a snippet for their config. A post-checkout that only checked out files does nothing, and so do hooks fired during a rebase. The background child points its stdio at null, so git doesn't wait for it.

Precedent: git hook config, git-lfs (refuses to overwrite a hook), pre-commit and lefthook (both refuse when core.hooksPath is set). Rejected: setting core.hooksPath ourselves, overwriting hooks, and a watcher daemon as the default.

D4

The schedule is opt-in and exists for fetchingchanges spec

D1 already keeps local commits current, so the hourly job is only for sync --fetch, to pick up commits teammates pushed. It's one user-level job that loops over the registry and runs at a random minute: launchd on macOS, a systemd user timer with Persistent=true on Linux (crontab if there's no systemd), and schtasks on Windows. doctor warns when the binary path stored in the job is stale. Board S3's options become: "Keep it current as you work" (D1, default), "Also after each commit or pull" (hooks), and "Also fetch every hour".

Precedent: git maintenance start in builtin/gc.c, including its random minute.

E · The command line

D12 · distribution
E1

Output conventions

Progress bars (indicatif) go to stderr, and only on a terminal. --json prints a versioned object, {"schema":1,…}, to stdout; new fields can be added freely, and removing one bumps the schema. It respects NO_COLOR and CLICOLOR_FORCE. An error says what went wrong, why, and what to try. Anything destructive asks first, and on a non-terminal it fails and names --yes. doctor prints one ✓ or ✗ line per check, with the exact command that fixes each ✗.

Precedent: clig.dev, brew doctor, flutter doctor.

E2

Exit codes are 0, 1, 2 and 3changes spec

0 means done, 1 an error, 2 bad usage, and 3 that status --check found a repo behind. Code 4 (lock busy) is gone because of D2. Code 5 (index format too new) is now code 1, with an error message that says so.

E3

init writes the manifest and asks before anything else

It always writes cartograph.yaml. Before adding a .gitignore entry, agent setup or hooks, it shows a preview of each change and asks. --yes accepts all of them. Without a terminal and without flags, it writes only the manifest and prints the next commands.

Precedent: husky init, changesets init, and lefthook, which refuses to touch hook config it doesn't own. Rejected: changing CLAUDE.md or AGENTS.md without asking.

E4

The command is cartograph; the packages need other names

On crates.io, cartograph belongs to a 2020 datacube project, and on npm to a 2022 router. Homebrew has nothing by that name. So: publish the crate as cartograph-cli, or ask the 2020 owner for the name. Releases are built with cargo-dist: shell and PowerShell installers, a Homebrew tap, an MSI, and winget later. On npm, publish a scoped package with one prebuilt package per platform, the way Biome does, so installs work offline and behind proxies.

Precedent: cargo-dist installers, Biome's npm packaging. Note: "Cartograph" is still a placeholder in PRODUCT.md. Decide the final name before the first crate or npm release.

E5

Cancel keeps the last complete index

On board 02, Cancel stops the run and leaves the previous index readable. Blobs already parsed stay in the cache, so the next run picks up where this one stopped. The board's copy says exactly that.

F · MCP and coding agents

open question 2 · X2
F1

Eight tools, not fourteenchanges spec

Read-only:

  • status, which also reports background jobs
  • find, which also covers entrypoints, through kind
  • describe, which also covers contracts
  • neighbors, with direction and cross_service; it replaces callers, dependencies and cross_service
  • path
  • impact, which takes paths, a ref, the working tree, or since; it replaces changes_since

Write: sync, which runs init when there's no index and defaults to a dry run in that case, and correct.

Why: more tools make an agent choose worse. Cursor sends at most 40 tools in total across all servers. Claude Code runs read-only tools in parallel, and Anthropic's guidance is to consolidate tools and return concise output.

Precedent: Writing tools for agents, GitNexus's 8 core tools. Rejected: keeping 14, and a single query-language tool that agents get wrong.

F2

Every answer is small and says how current it is

content holds compact Markdown for the model. structuredContent holds the full JSON, with an outputSchema. response_format is concise or detailed, the limit is 50 with an opaque cursor, and the target is under 10k tokens; Claude Code warns above 10k and cuts off at 25k. Each result carries freshness: each repo's indexed commit, its HEAD, how many commits behind it is, and whether a sync is running. The server's instructions field stays under 4,096 characters, because with tool search it decides whether an agent finds Cartograph at all.

F3

Long work returns a handle

sync returns its result if it finishes within wait_ms (default 15 s). Otherwise it returns a job_id, which status reports on. It sends progress notifications when the client provides a progress token. The MCP Tasks extension is added later, and only for clients that ask for it.

Why: Tasks moved out of the core spec into an extension and changed shape on the way. Claude Code supports them only in beta, and Cursor doesn't list them. Polling works on every client.

Precedent: Claude Context's index_codebase with get_indexing_status. SEP-2663.

F4

stdio by default; HTTP is opt-in and locked down

--http exists for one server shared by several clients. It binds only to loopback, checks Host, refuses any Origin not on the allow list, and needs a 256-bit token from a file only you can read. Clients pass the token through an env var or Claude Code's headersHelper, never written into a committed file.

Precedent: MCP transports: servers must validate Origin, and local servers should prefer stdio.

F5

Agent setup is per user by default, not per repochanges spec

cartograph agents install writes user-level config:

  • claude mcp add --scope user
  • ~/.cursor/mcp.json
  • ~/.codex/config.toml
  • VS Code's user mcp.json

The registry already lets cartograph mcp run without a path, so one entry covers every workspace. --project writes config into the workspace folder. --per-repo writes it into every repo, and is never the default.

Why: writing into each repo means a commit in N repos. Teammates without the binary would get a server that fails to start, and in -p mode Claude Code loads a project's servers without asking.

Precedent: Serena's --scope user setup, and GitNexus's setup, which writes global config.

F6

Claude Code gets a plugin; other agents get a short instruction blockchanges spec

The Cartograph repo publishes its own plugin marketplace. The plugin bundles:

  • the MCP server
  • a skill holding the procedures: check status, run impact before editing across services, and treat "guessed" results as leads
  • a SessionStart hook that prints one line about how current the index is

For Codex, Copilot and Cursor, a marked block of about five lines goes into AGENTS.md, copilot-instructions.md or a .mdc rule. For Claude Code without the plugin, the block goes into CLAUDE.local.md, which is personal and not committed. Writing it into the shared CLAUDE.md takes --shared. The block holds pointers only, never state, and never @-imports CARTOGRAPH.md.

Why: a plugin is one versioned unit that changes no shared files. An import loads the whole file into every session and goes stale during it. agents install detects the plugin, so hooks don't run twice.

Precedent: Claude Code plugins, memory docs, GitNexus's <!-- gitnexus:start --> blocks. Rejected: a sync after every edit; a plugin as the only way to install.

F7

CARTOGRAPH.md stays, kept out of git, generated from status

The MCP status tool and the cartograph://status resource are the source of truth. CARTOGRAPH.md is the same data, written for people and for agents that don't use MCP. It's rewritten after every sync, and it now also says where the index lives (B1).

F8

Text from the repo is treated as data everywhere (X2)

Tools return structure by default. Comments, docstrings and README text come back only when asked for, truncated, in fields labelled untrusted_text that say where the text came from. Repo text never goes into tool descriptions, server instructions, CARTOGRAPH.md or the instruction blocks, because those load automatically into every session. No tool runs code or uses the network. sync only acts on repos in the registry. correct stores data, never instructions.

Precedent: Spotlighting (Microsoft), the MCP spec's requirement that servers sanitise tool output, and Context7's prompt-injection incident.

G · AI, and the Claude Code idea

stage 6 · X2 · D15
G1

Don't build the Claude Agent SDK in. Put Cartograph inside your Claude Code instead.

The idea is sound and the goal is right: use the Claude Code you already pay for, with the map. The way to get there is the other direction. Cartograph is an MCP server and plugin inside your own Claude Code (F5, F6). Your login, your billing and your agent stay yours, and the same setup works for Codex, Cursor and Gemini.

Why not the SDK:

  • Policy. Anthropic's terms say third-party apps may not offer claude.ai login or route requests through Pro, Max or other plan credentials. The exception is a user running the unmodified claude binary themselves.
  • Size and runtime. The SDK runs the Claude Code binary, about 364 MB per platform, and needs Node. The Rust core can't host it.
  • Risk. A full coding agent with shell and edit tools, reading text from indexed code, turns prompt injection into code execution.
  • Naming. The feature can't be called "Claude Code".

Source: Claude Code legal and compliance, Agent SDK overview. Anthropic has changed this policy several times this year, so read it again before any change to G2.

G2

Later, an "External agent" choice in Ask, over ACP

The Ask panel can run the user's own agent over the Agent Client Protocol: Claude Agent through claude-agent-acp, Codex or Gemini CLI. Cartograph starts the agent as a subprocess and passes only its read-only MCP tools to session/new. It offers no file system or terminal capability, rejects every permission request that isn't for a Cartograph tool, and caps the number of turns. You sign in inside the agent. Cartograph never sees, stores or relays credentials, and never shows its own "Sign in with Claude" button. This comes after stage 6 ships, not before.

Precedent: Zed's external agents ("Claude Agent owns its own authentication and billing"), ACP, claude-agent-acp. Rejected: shelling out to claude -p, which is a grey area on policy, loads the project's hooks and .mcp.json, and has an output format that's brittle to parse.

G3

The Ask loop runs in Rust, and providers come from genai

The app, cartograph ask and the HTTP API share one agent loop in the binary, so citations are checked in one place and keys never reach the browser. The genai crate speaks the native OpenAI, Anthropic, Gemini and Ollama APIs, plus any OpenAI-compatible endpoint, and the current lib/ai.ts presets map onto it. The provider registry is a small TOML file. Anthropic is used through its native API with an API key, so features like citations and caching work. When Cartograph runs as an MCP server it needs no model at all: the host agent does the reasoning.

Precedent: Codex CLI and Goose both run their agent loop in Rust. Rejected: the Vercel AI SDK in Next.js, which would tie the loop to Node so the CLI needs a second copy; a LiteLLM proxy, which is another service to run.

G4

API keys go in the OS keychain

The keyring crate stores them in Keychain, Credential Manager or Secret Service. CARTOGRAPH_AI_KEY and CARTOGRAPH_AI_BASE_URL override it (board G15). A file only you can read is the fallback on Linux with no keychain. The browser only learns whether a key is set. Keys in localStorage today are moved once and then deleted from it.

Precedent: gh; uv, which vendors keyring-rs.

G5

Citations point to results from this turn, and are checked deterministically

Each row a tool returns gets a short handle, like e3, and the model cites handles, never raw ids. A citation stands only if all of these hold:

  • the handle came from this turn
  • the object still exists
  • its interval covers the date being asked about
  • every identifier and relationship claimed in the sentence is among that sentence's citations

Citations that fail are removed, and sentences left with none are shown as unsupported. If more than 30% of sentences are unsupported, the model gets one repair attempt. If that fails too, the answer comes from the graph engine alone, without the model's wording.

Precedent: Anthropic's search-result citations, ALCE. Rejected: a model judge as the main check, which is slow and can itself be injected.

G6

Injection can at worst cause a wrong answer, which citations catch

Ask's tools are read-only graph tools, with no shell, no writes and no network. Code-derived text sits inside randomised delimiters and is marked as data. Answers render as plain text. Links come only from checked citations, never from URLs or images the model writes, so there's no way to send data out. Together with F8, this closes X2.

Precedent: Spotlighting, and Willison's dual-LLM pattern. Rejected: a full CaMeL interpreter for now. Revisit it if any write tool is ever added.

G7

No embeddings to start with

Retrieval uses graph traversal, SQLite FTS5 over names, paths and docstrings, and tool calls. Summaries stay off by default, suggest a local model, and are cached by blob id, model id and prompt version. If embeddings are added later, they're built over summaries rather than raw code, with fastembed-rs and sqlite-vec in the same file.

Precedent: Aider's repo map, built from tree-sitter tags and PageRank; Claude Code's agentic search; Continue and Sourcegraph moving away from embeddings; Greptile finding that summaries embed better than code. Rejected: LanceDB, a second store; embedding raw code chunks.

G8

"Ultra" becomes a budget, not the whole map

It starts from the evidence, adds neighbours ranked by personalised PageRank, and stops at half the model's context window, capped at about 100k tokens. It says how many nodes it left out. The retrieval inspector (board A6) shows every tool call, the tokens for each block against the budget, which handles were cited or dropped, and the system prompt.

Why: models recall facts in the middle of long contexts less well (Lost in the Middle), and a multi-repo map soon outgrows any context window.

G9

Ask history goes in its own file, next to the index (D15)

It's ask.db in the same data folder, because the index can be rebuilt and history can't. Each turn stores the question, the date asked about, the index's fact hash, the model id, the tool calls, the answer and the citation results, and never any keys. History can be re-run as of another date. An answer is marked stale when ids it cited no longer exist, and cartograph ask --forget wipes everything.

H · Extracting links

X7 · X8 · X9 · X11 · board decisions
H1

tree-sitter for every language, and oxc's resolver for TypeScript and JavaScriptbenchmark

Imports are syntax, and tree-sitter parses old blobs from history without a toolchain or a build. oxc_resolver handles tsconfig paths and extends, package exports and imports, pnpm symlinks and Yarn PnP, natively in Rust. Stage 2 needs only small resolvers: Go reads go.mod and go.work, Python reads pyproject.toml, and PHP reads Composer's PSR-4 map. SCIP is import and export only, in stage 5.

Precedent: Sourcegraph's split between search-based and precise code navigation, and oxc resolver. Rejected: swc or oxc_parser, which cover TypeScript only; go/packages and SCIP as the main source, because they need a build for every commit. Before code: check oxc's claimed speed-up on a real monorepo.

H2

Confidence comes from the class of evidence, not from cut-offs on the score

exact (0.90–1.00): both ends are anchored. A contract operation matches on both sides, or a literal method and path match a parsed route, or a literal topic or table name appears on both ends.

likely (0.60–0.89): one end is literal and the other is resolved through config or env, or a call through a generated client is mapped to its spec.

guessed (0.30–0.59): a partial path match, string concatenation, or a match on name only. Below 0.30, the link is stored but hidden by default.

Within a level, the score combines fixed weights per evidence type as 1 − ∏(1 − wᵢ), clamped to that level's band. This settles the open decision on cut-offs.

Why: adding a new kind of evidence can't quietly move a link from one level to another, and each word has a stated meaning. Precision per level is measured on the 17 apps in the Code2DFD dataset and published, the way CodeQL publishes @precision.

Precedent: Sourcegraph's precise versus search-based results, CodeQL @precision, Semgrep's confidence levels, and a 2024 comparison of architecture-recovery tools. Rejected: a bare score with cut-offs; a model trained to calibrate scores, which has no training data and can't explain itself.

H3

Corrections use keys a person can read, and every one needs a reason

version: 1
corrections:
  - remove: { kind: http, from: storefront, to: billing-api, op: "GET /legacy/invoice" }
    reason: Dead route behind a feature flag removed in 2024.
  - retarget: { kind: event, from: orders, topic: "order.paid", to: ledger }
    reason: Ledger consumes through the outbox relay.
  - set: { kind: http, from: web, to: auth, op: "POST /session", confidence: exact }
    reason: Checked by hand against the gateway config.
  - add: { kind: http, from: mobile-bff, to: orders, op: "GET /orders/{id}" }
    reason: Called through the API gateway, which isn't in the workspace.

The indexer resolves each key to lineage ids and stores that binding, so a correction survives a rename (X7). cartograph check fails on a correction that no longer matches anything; set stale: error | warn | off, default error. The precedence stays as parsed < contract < config < runtime < correction, and each link records which layer won. This settles the open decision on YAML keys, and adds add, which the first draft didn't have.

Precedent: import-linter's ignore_imports, where unmatched ignores are an error by default; Backstage entity refs; the SCIP symbol grammar. Rejected: keying by lineage id, which people can't write; keying by path only, which breaks on renames.

H4

Adapters are tree-sitter queries first, a subprocess second (X8)

(a) .scm query files that use Cartograph capture names (@route.method, @route.path, @http.call.url, @event.publish.topic, @db.table), the same convention as tree-sitter's tags.scm. (b) For anything a query can't express, a subprocess that prints NDJSON facts:

{"schema":1,"kind":"http.call","repo":"web","commit":"77c0e2b","path":"src/api.ts",
 "span":[12,4,12,38],"attrs":{"method":"GET","url":"/orders/{id}"},
 "evidence":{"type":"literal","text":"fetch(`/orders/${id}`)"},"extractor":{"name":"fetch","version":"1.2.0"}}

"Request an adapter" on board S5 opens the local guide to writing one, and links to the issue template on GitHub. WebAssembly plugins are deferred until third parties ship binaries.

Precedent: tags.scm, ast-grep rules, SCIP's one-indexer-per-language model. Rejected: stack-graphs, which GitHub archived; Glean, which needs a server.

H5

Generated API clients are found by their markers and matched by path (X9)

Detect generated files by // Code generated … DO NOT EDIT., by .openapi-generator/FILES, and by orval or openapi-typescript banners. Find the spec through the generator's config. The literal method and path template inside the generated code are matched to the spec operation, and the function is recorded as an alias for its operationId. Calls through that function are likely, and become exact when the spec also matches the server's parsed route.

Precedent: Go's generated-code convention, oapi-codegen's headers. Rejected: predicting method names from operationIds, which breaks between generator versions. Before code: confirm the exact orval and openapi-typescript banner text.

H6

Architecture rules live in cartograph.yaml (X11, D8)

rules:
  - name: web-no-direct-db
    severity: error                 # error | warn | info
    forbid:
      from: { tags: [layer:web] }
      to:   { kind: db_table }
    min_confidence: likely          # guessed links never fail CI
baseline: cartograph.baseline.json  # known violations, so old repos can adopt rules

Rules are checked by cartograph check and in the app's rules view. Selectors match tags, service, a path regex with $1 captures, and link kind.

Precedent: dependency-cruiser, Nx module boundaries, go-arch-lint, import-linter. Rejected: ArchUnit-style rules written in code, which tie rules to one language.

I1

sigma.js 4 with graphology for the map, keeping SVG for small viewsbenchmark

Both are MIT-licensed, render with WebGL, thin out labels with a label grid, and pick with the GPU. The graph data (graphology) is separate from the renderer, which fits a model where Rust owns the data. Level of detail swaps the graph per level instead of drawing 60k files at once. d3-force SVG stays for views under about 2,000 elements and for SVG export.

Precedent: Gephi Lite, which is GPL, so read it but don't copy it. sigma performance guide. Rejected: Cosmograph, which is CC-BY-NC; deck.gl, PixiJS and regl, which would mean rebuilding picking and labels; Ogma, which is commercial. Before code: run sigma's benchmark on a 60k-node, 200k-link fixture.

I2

Layout is computed in Rust at index time, stored, and stable over time

Layout runs top-down: services first, then modules inside each service's area, then files, so a change in files can't move services. Each snapshot starts from the previous one. New nodes start at their parent's position, and nodes that didn't change are pinned. The browser only reads positions, and runs ForceAtlas2 locally only when you expand something.

Watch the licence: the forceatlas2 crate is AGPL. Use graphology/rust-fa2, or about 300 lines of our own Barnes-Hut. Precedent: CodeCharta's stable maps, and research on stable treemaps. Rejected: running force layout in the browser on load, which differs on every load, so scrubbing jumps around.

I3

A table view and a keyboard walk (D3)

The canvas is hidden from screen readers. Next to it are virtualised, sortable tables of nodes and links, which follow the same filters, date and level as the map. The keyboard walk is built on data-navigator:

  • arrow keys move between siblings
  • Enter goes down a level, and Escape goes up
  • one key cycles through linked nodes
  • a live region announces "module X, 12 incoming, 4 outgoing"

The result is audited against Chartability.

Precedent: data-navigator, Olli, Highcharts' keyboard model.

I4

Comparing two dates overlays both on one layout (D7)

Added items show green, removed ones as a red ghost, changed ones amber, and everything unchanged is dimmed. A toggle shows the two dates side by side, with the camera and selection linked. The table has a matching filter for differences. This only works because I2 keeps positions stable.

Precedent: CodeScene's coupling trends, CodeCharta's delta mode.

I5

Toasts for now, an activity list for later (D5)

Toasts can be dismissed with the keyboard and are announced to screen readers. A bell with an unread count opens the activity list, stored in ask.db's sibling tables. The app doesn't send OS notifications by default; an opt-in one for "a long index finished" can come later.

Precedent: VS Code notifications.

I6

Below 900 px, the table is the default view (O2)

The map moves to a tab. On touch screens, file-level hover and the label grid are turned off. Settings stack into one column, with the left menu becoming a select.

I7

Share links are view links that any local copy can open (D9)

The view state lives in the hash, so a link is cartograph://acme#t=2019-04&focus=billing-api. On Windows and Linux the CLI registers the scheme. On macOS, which needs an app bundle to register one, you paste the link into "Open link" in the app or run cartograph open <link>. Exports are PNG from the canvas and SVG from the SVG renderer.

Rejected: Tauri only to get deep links, which would mean signing and packaging for every OS.

I8

Approve the colour rule, and write the boards back into DESIGN.md (O4, D13)

Domains take the six pinned hues, services take tints of their domain's hue, and everything else is steel. At 62 services this is the only scheme that stays readable. It's what every board already assumes, and it keeps the pinned reference's hues instead of adding new ones. Then write the theme tokens, chip states, view tabs and settings menu into DESIGN.md, so the code has one source.

I9

One app shell (D4), and the remaining screens

The shell is the A boards' header with the view tabs, plus the S boards' settings menu; board 15 moves to it.

The remaining flows:

  • First run (D2) offers three ways in: add a workspace in the app, open an existing index, or try the demo.
  • The add-workspace wizard (D1) needs its other steps drawn. Step 1 is "pick a workspace file or folder", using the discovery from C1 and C2. Step 3 reviews the services found by C6. Step 4 is the first index, then the map.
  • Empty states (O1) follow one pattern. Each says what will appear, why it isn't there yet, and the one action that fills it.
  • "Trace on the map" (D6) highlights what can be reached, dims the rest, and shows a Clear chip.
  • Recovery (D10): every warning row already has an action, per board decision 5. Undoing a correction reverts that entry in the override file, and the history is the file's own git log.
  • Owners (D14) come from CODEOWNERS as a node attribute and a filter. A team view comes later.
  • Previous and Next commit on board A5 step along the first-parent timeline, or along a branch overlay's commits when one is open.

What the earlier spec got wrong

now updated
  • The index was in the workspace folder. Now it's in the data folder (B1).
  • Hooks or a schedule kept it current. Now reads keep it current, and both are optional (D1, D4).
  • There were 14 MCP tools. Now there are 8 (F1).
  • Agent config was committed to the workspace folder. Now it's per user, and Claude Code gets a plugin (F5, F6).
  • The CLAUDE.md block was shared by default. Now it goes in CLAUDE.local.md unless you pass --shared (F6).
  • Exit codes 4 and 5 are gone (E2).
  • There was no verify or check. Both are added (B4, H3, H6).
  • An MCP init tool started background jobs. Now sync does init, and long work returns a job handle (F3).
