Understand a codebase without reading all of it.

Cartograph draws a workspace as a map of services, modules and files, says in plain words what each one does, and ties every link between them to the commit that added or removed it.

What it does

Cartograph indexes the full git history of your code and turns it into a map you can read, scrub through time and ask questions of. Everything runs on your machine.

Point it at your code

Give Cartograph one git repository, a folder of repositories or a VS Code workspace file. It reads the history straight from git, not from your working tree, and it never writes to your repositories.

It reads TypeScript, JavaScript, Go, Python and PHP, and finds the services inside each repository from their manifests. Later runs only process the commits that are new.

# one repository
cartograph index .

# every repository in a folder
cartograph index ~/code/acme

# a VS Code workspace file
cartograph index acme.code-workspace

One map, three layouts

Network groups modules and files around the service they belong to. Ontology arranges the same nodes by hierarchy, with the workspace at the centre and services, modules and files around it. Adaptive treats links like springs and lets you drag nodes where you want them.

Switching layout moves every node to its new position, so you can follow where things went.

Focus on one node

Select a file, module or service and the map narrows to it. What it depends on sits on one side, what uses it on the other. You see what a file touches before you open it.

Scrub through history

Drag the scrubber or step one commit at a time. The map shows the links that existed on that date, and each step shows which links that commit added and which it removed.

Figures for every node

A side panel shows links, cross-service links, churn, fan-in and fan-out, with a trend chart, the commits that changed the node's relationships and its strongest links. Fan-in is how many links point at a node. Churn is how many links were added or removed in the 90 days before the selected date.

Ways to find things

A workspace tree, search, pins for the nodes you keep returning to, and a filter that shows only the link types you care about.

Open to other tools

An MCP server exposes the same map, so a coding agent can ask what a change will break before it makes one. You can ask too

How the map is modelled

Three ideas carry it: a hierarchy of nodes, typed links between them, and a commit recorded on every link.

Four levels, each with a description

Every node says what it does in a sentence, written from the code by the model you choose, so you can stop at the level that answers your question.

  1. Workspace northwind

    Six services and their shared libraries, mapped as one workspace.

  2. Service shared-libs

    Libraries imported by every service: logging, event contracts, money.

  3. Module events

    The event bus contract shared by producers and consumers.

  4. File schema.ts

    Typed schemas for every domain event. Breaking changes here ripple to all consumers.

Names and descriptions from an example workspace.

Five kinds of link

A link is typed, so "imports it" and "calls it over HTTP" are never drawn as the same thing.

Imports
One file imports another.
Calls
Code in one file calls a function in another.
HTTP
A client in one service requests a route in another.
Events
A file publishes to an event bus, or consumes from it.
Database
A file reads or writes a database.

Several repositories and services sit in one map. A link whose two ends are in different services is a cross-service link. Those are drawn on the map and counted for every node. Links found by matching HTTP routes, event topics and tables carry a confidence level, so an inference is never drawn as a certainty.

Ask the map

Answers come with their evidence. Each one is worked out by walking the graph, and shows the files and commits it used. Click any of them to go there on the map and check the answer yourself.

Questions you can ask

  • What breaks if I change schema.ts?
  • How does checkout reach stripeAdapter?
  • What changed in billing since June?
  • What does auth-service do?

Bring your own model

The composer has a model and reasoning-effort picker, set up from the settings in the interface. It works with any OpenAI-compatible endpoint, hosted or local: Ollama, LM Studio, OpenRouter, OpenAI, Gemini, or Anthropic's compatibility endpoint.

The model writes the answer. The facts still come from the map, and every file and commit it mentions stays clickable. With no model set up, answers come from the map alone and nothing leaves your machine.

The research behind the indexer

The usual way to learn when each link appeared is to check out every commit and index the code again. On a real history that is tens of millions of parses. Cartograph's indexer uses a method the project calls content-addressed fact replay, and parses each version of a file once.

Measured on a TypeScript monorepo with the research script: imports only, one thread, one run, Apple M4. The script is in the repository, so you can run it on your own history.

Parse each version of a file once

Facts are keyed by content.

  • What a file says, such as what it imports, calls, serves or publishes, depends only on its bytes. Git already gives those bytes a name, the blob id.
  • Facts are extracted once per blob id and kept. A file that sits unchanged through 5,000 commits is parsed one time, and a revert costs nothing.

Re-resolve only what a commit can affect

A reverse index instead of a re-index.

  • What a reference means depends on the rest of the tree. ./db points somewhere else once db.ts moves.
  • Each reference waits on the paths that could satisfy it. When a commit adds or deletes a path, only the references waiting on that path are looked at again.
  • A link opens when its first supporting reference resolves and closes when the last one goes. Those two commits are what the map shows you.

One timeline for every repository

Cross-service links get commits too.

  • The histories of all repositories in a workspace are merged into one ordered timeline.
  • An HTTP call in one repository and the route it reaches in another become one link, dated by whichever commit, in either repository, completed the match or broke it.

Later runs cost what changed

And every result can be checked.

  • A later run parses only the blobs it has not seen and replays only the new commits.
  • Rebased or force-pushed history is handled by rewinding to the last commit both histories share.
  • The replayed map at any commit must equal a from-scratch index of that commit. That comparison is the indexer's main test.

Where it comes from

The parts are established work: content-addressed archives (Software Heritage), per-file analysis with deferred resolution (GitHub's stack graphs), oldest-first replay of added and removed hops (Sourcegraph's Rockskip), and anchors with deltas for graphs that change over time (DeltaGraph, AeonG). The combination is Cartograph's own. It is an engineering synthesis, not a peer-reviewed result.

There is no hosted version, no account and nothing to pay for. Cartograph is code you clone and run.

Run it locally

You need Node.js and pnpm.

git clone https://github.com/ax3cubed/cartograph
cd cartograph
pnpm install
pnpm dev

Then run cartograph index on a repository or a folder of them, and open the local address that pnpm dev prints.
