Understand a codebase without reading all of it.

Cartograph draws a workspace as a map of services, modules and files, says in plain words what each one does, and ties every link between them to the commit that added or removed it.

What works today

Everything in this section runs now, in version 0.1, on the demo workspace that ships with the project: six services, 32 files and 21 months of commits. It does not read your own repositories yet. That part is on the roadmap.

One map, three layouts

Network groups modules and files around the service they belong to. Ontology arranges the same nodes by hierarchy, with the workspace at the centre and services, modules and files around it. Adaptive treats links like springs and lets you drag nodes where you want them.

Switching layout moves every node to its new position, so you can follow where things went.

Focus on one node

Select a file, module or service and the map narrows to it. What it depends on sits on one side, what uses it on the other. You see what a file touches before you open it.

Scrub through history

Drag the scrubber or step one commit at a time. The map shows the links that existed on that date, and each step shows which links that commit added and which it removed.

Figures for every node

A side panel shows links, cross-service links, churn, fan-in and fan-out, with a trend chart, the commits that changed the node's relationships and its strongest links. Fan-in is how many links point at a node. Churn is how many links were added or removed in the 90 days before the selected date.

Ways to find things

A workspace tree, search, pins for the nodes you keep returning to, and a filter that shows only the link types you care about.

Ask the map

Type a question such as "What breaks if I change schema.ts?" The answer comes from walking the graph, and lists the files and commits it used. More on Ask the map

How the map is modelled

Three ideas carry it: a hierarchy of nodes, typed links between them, and a commit recorded on every link.

Four levels, each with a description

Every node says what it does in a sentence, so you can stop at the level that answers your question.

  1. Workspace northwind

    Six services and their shared libraries, mapped as one workspace.

  2. Service shared-libs

    Libraries imported by every service: logging, event contracts, money.

  3. Module events

    The event bus contract shared by producers and consumers.

  4. File schema.ts

    Typed schemas for every domain event. Breaking changes here ripple to all consumers.

Names and descriptions taken from the demo workspace.

Five kinds of link

A link is typed, so "imports it" and "calls it over HTTP" are never drawn as the same thing.

Imports
One file imports another.
Calls
Code in one file calls a function in another.
HTTP
A client in one service requests a route in another.
Events
A file publishes to an event bus, or consumes from it.
Database
A file reads or writes a database.

Several repositories and services sit in one map. A link whose two ends are in different services is a cross-service link. Those are drawn on the map and counted for every node.

Ask the map

Answers come with their evidence. Each one is worked out by walking the graph, and shows the files and commits it used. Click any of them to go there on the map and check the answer yourself.

Questions it answers in the demo

  • What breaks if I change schema.ts?
  • How does checkout reach stripeAdapter?
  • What changed in billing since June?
  • What does auth-service do?

What is shipped and what is not

Cartograph is an early prototype. The map interface is real and runs on demo data. The part that reads your repositories is still being built. Here is exactly where each piece stands.

Shipped

Version 0.1: the map

Works today, on the bundled demo workspace.

  • The interactive map, running on a demo workspace of six services, 32 files and 21 months of commits
  • Network, Adaptive and Ontology layouts, with a morph between them
  • Focus view showing Depends on and Used by
  • A time scrubber that steps commit by commit and shows links added and removed
  • A side panel with links, cross-service links, churn, fan-in and fan-out, a trend chart, relationship changes and strongest links
  • Workspace tree, search, pins and a link-type filter
  • Ask the map, with the files and commits behind each answer as clickable evidence

Being built

The indexer, then everything that depends on it

Not usable yet. Until it lands, the map shows demo data only.

  • The indexer: a command-line tool that reads the full git history of one repository or many and writes the real map
  • Its design parses each distinct version of a file once and replays history, instead of re-indexing the code at every commit

One early experiment, with a caveat

To test the replay design, a throwaway script with a simplified extractor was run over a real TypeScript repository with 35,000 commits. It processed the whole first-parent history in 4.4 seconds, with 719 times fewer parses than re-indexing every commit. This was an experiment, not the finished indexer. It says the design is worth building. It is not a benchmark of something you can run.

After the indexer

  • Go, Python and PHP support
  • Cross-service link detection for HTTP routes, events and tables, with a confidence level on every link
  • Symbol-level calls
  • Summaries written by a model of your choice
  • An MCP server, so other agents can query the map

Open source, MIT licensed

There is no hosted version, no account and nothing to pay for. Cartograph is code you clone and run.

Run it locally

You need Node.js and pnpm.

git clone https://github.com/ax3cubed/cartograph
cd cartograph
pnpm install
pnpm dev

Then open the local address that pnpm dev prints. The map opens on the demo workspace.
