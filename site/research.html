Cartograph research note · 10 November 2026

Dating every dependency in a codebase without re-indexing its history

Cartograph shows when each link between two files appeared and when it went away. This note tests the method its indexer is designed around, on a real repository with 35,439 commits and on a folder of 43 repositories, and reports what held up and what did not.

Three results changed the design. Caching by content is not where the speed comes from on a single line of history. The planned snapshot anchors are slower than a plain scan at this size. And extraction is mostly git reading objects, not parsing; how well it spreads across cores could not be settled on a busy laptop. Details are in what the results change.

1. The problem

A code map that can be scrubbed through time needs the dependency graph at every commit. Each link needs two dates: the commit that added it and, if it is gone, the commit that removed it. The map must also cover several repositories at once, because the links people most want to see cross a repository or service boundary.

The direct way is to check out every commit and index the tree. The cost is one parse per file per commit. On remotion that is 41,714,790 parses for a history in which only 103,347 distinct file versions ever existed.

The question for this note is how little work is actually needed, and whether a cheaper method gives exactly the same answer.

2. The model

The method rests on one split. What a file says depends only on its bytes. What that means depends on the rest of the tree.

Tree Tt
The mapping from path to git blob id after timeline step t. A step is one commit on a repository's first-parent chain.
Facts F(b)
What the blob b says, extracted from its bytes alone: the references it makes ("./db", "@remotion/renderer") and what it provides (a package.json provides its package name). F is a pure function, so it is computed once per blob id.
Keys K(Tt)
Everything a reference could resolve to at step t: every path in the tree, and every package name provided by a package.json in it.
Reference r
A pair (file, specifier) with an ordered list of candidate keys, cand(r). For ./db from src/a.ts the list is src/db.ts, src/db.tsx, …, src/db/index.ts, ….
Resolution
resolve(r, Tt) is the first key in cand(r) that is in K(Tt), or nothing.
Link
A typed pair (source, target). It is alive at t when at least one reference from the source resolves to the target. Its history is a set of half-open intervals [added, removed).
Roll-up
Each file belongs to a module, a service and a repository. A file link lifts to every pair of ancestors that differ, so a service-level link is the count of file links beneath it. This is a quotient of the file graph, and its intervals follow from the file intervals.

The property that makes a shortcut possible. resolve(r, T) can only change when a key in cand(r) enters or leaves K(T). So if every reference is registered under each of its candidate keys, a commit that adds or deletes a key needs to revisit exactly the references registered under that key and no others. By induction over the timeline, the replayed set of links at step t equals the set computed from Tt alone. The experiments check this at 24 commits against an index that shares no state with the replay.

3. The method

  1. Walk. One streaming git log --first-parent --reverse --raw --no-renames per repository. Each commit yields the paths it changed and their new blob ids. Dates are corrected to be strictly increasing along the chain, because committer dates are not.
  2. Extract. Compute F(b) for each blob id not seen before, in parallel. This is the only step that reads file contents.
  3. Merge. Order the commits of all repositories on one timeline by corrected date.
  4. Replay. Apply the steps in order. Keep the tree, the references, and a reverse index from key to the references waiting on it. When a file changes, diff its old and new facts. When a key appears or disappears, re-resolve only the references waiting on it. Count the references supporting each link; write an interval when the count leaves or returns to zero. A link that closes and reopens inside one commit never left.

One reference over five commits. It is re-resolved only when a key it waits on appears or disappears (c2, c4, c5). a.ts is parsed when its own bytes change (c1, c3) and never because another file changed.

4. Setup

The experiments are one Node script, docs/research/bench.mjs, with no dependencies. It reads repositories through git plumbing commands and writes nothing to them. It tracks two kinds of link: a relative import that resolves to a file, and a bare import that resolves to the package.json declaring that package name. The second kind is what makes links cross package and repository boundaries.

5. Results

5.1 How much work is avoided

How many parses does each strategy need for the same history?

StrategyParses, first-parent chainParses, every commit
Index every commit from scratch41,714,790not measured
Re-parse only changed paths105,293379,197
Changed paths, cached by blob id103,347145,119

Indexing only what each commit changed removes 395 of every 396 parses. That is where almost all of the saving is. Of the 103,347 distinct blobs, 57,060 are source files and 46,287 are package.json versions, because this monorepo bumps every package on each release.

Caching by blob id adds only 1.8% on top of that on a single first-parent chain. A file rarely returns to earlier content on one line of history. The cache matters when the same content is met more than once: indexing every commit rather than only the main line needs 2.6× fewer parses with it, because a change is seen once on its branch and again in the merge. It also makes a second run, a rebased history or a second clone cost nothing for content already seen.

5.3 Against indexing every commit

How long would the direct method take, measured rather than counted?

The cost of one from-scratch index grows with the tree, from 22 ms early in the history to 260 ms at head. The mean over the samples is 161 ms. Across 9,498 commits that is about 1,528 seconds, or 25 minutes. Fact replay covers the same commits in 4.6 s, which averages 0.49 ms per commit.

About 330× faster at the median, 490× on the best run.

The total for the direct method is extrapolated from the samples. It was not run in full. Two earlier runs of the whole suite the same day gave ratios of 266× and 364× at the median, so read this figure as roughly 300×.

5.4 Is the answer the same?

Does the shortcut give exactly what the direct method gives?

At each of the 24 sampled commits the from-scratch index above was compared with the replayed state at that step, by hashing the sorted list of (path, blob id) pairs and the sorted list of links.

  • Files: the replayed tree equals git ls-tree at all 24 commits. This checks the walk, including how merge commits are diffed.
  • Links: the replayed links equal the from-scratch links at all 24 commits.
  • Intervals: rebuilding the link set at each sampled step from the written intervals gives the same set again.
  • Workspace: the final state of all 43 repositories equals a from-scratch index of each repository's head.

No difference found in any comparison, on any corpus.

The from-scratch index shares the extraction pattern and the candidate rule with the replay, so this shows the replay loses nothing. It does not show the extraction itself is right. See limits.

5.5 What the reverse index buys

If references were simply re-resolved whenever a commit adds or removes a file, how much slower is replay?

Replay variantResolutions, remotionTime, remotionResolutions, workspace
Re-resolve every live reference on each structural commit37,817,9752,828 ms89,488,857
Reverse index60,039348 ms103,200

Both variants wrote identical intervals. The reverse index does 630× fewer resolutions and replays 8× faster (best of three for each). At this size the simpler variant would still finish in seconds, so the reverse index is not what makes the method feasible here. It is what keeps replay independent of tree size, and resolution in this experiment is cheap: a few map lookups. With real module resolution each call costs far more, and the gap in time moves towards the gap in count.

Each worker runs its own git cat-file --batch. The sweeps were run minutes apart on the same machine. Reading only was tried once in sweeps 1 and 2.

Reading the blobs out of git is most of the cost. In the three sweeps where the reading-only figure is usable it is 64% to 78% of the one-worker time. The pattern match is the smaller part.

How far parallelism helps could not be settled on this machine. The fastest setting was 4, 2, 8 and 2 workers in the four sweeps, and the best speed-up over one worker ranged from 1.5× to 2.5×. The laptop was running other work throughout, and the differences between settings are smaller than the differences between sweeps. This needs a quiet machine.

A real parser will move the balance. Parsing costs more per byte than a regular expression, so more of the time will be work that can be spread across cores.

5.7 Later runs

What does it cost to take in new commits?

The history was replayed up to 100 commits before head. Then the remaining 100 commits were walked in a new git process, their 808 unseen blobs extracted, and the steps replayed. The final state was identical to the full run.

5.8 Jumping to a date

Does the map need stored snapshots to show the links at an arbitrary commit?

The design called for an anchor every K steps: the set of live links, so that a jump reads one anchor and applies at most K steps of changes. The alternative is to store only the intervals and scan them.

StrategyExtra entries storedTime per query
Scan all 36,193 intervals00.06 ms
Anchor every 64 steps1,648,7150.41 ms
Anchor every 256 steps422,4810.42 ms
Anchor every 1,024 steps109,4240.42 ms
Anchor every 4,096 steps30,1200.55 ms

The scan wins at every anchor spacing tried. Copying an anchor into a set costs more than testing two numbers on every interval. At the scan's rate, one 16 ms frame covers about 10 million intervals. Anchors are worth building only past that size, and a sorted index on the interval bounds would likely come first.

5.9 Several repositories on one timeline

Do links that cross repositories get dates too?

All 43 repositories under one folder were walked, merged by corrected commit date into 14,730 steps and replayed together. Blob ids met in more than one repository were extracted once (395 of them).

  • 153 links crossed a repository boundary at some point, between 4 pairs of repositories. 105 are still present.
  • Most are a file in an application repository importing a package whose source lives in the remotion repository in the same folder. The most common target is the remotion package itself, with 114 links.
  • Each of these links is dated on the merged timeline, by a commit in whichever repository completed it.

This demonstrates the mechanism for package links. HTTP routes, events and tables are not extracted in this experiment.

5.10 How long links live

The intervals are data in their own right. What do they say?

9,984 of 34,604 links were removed at some point. About 4% are gone within a week of being added, which is churn inside a piece of work. After that the curve flattens: 74% are still present after one year and 67% after two. The estimated median lifetime is about 5 years.

A file moved with identical content is treated as the same file, which joined 1,589 intervals. A file moved and edited in the same commit still counts as a removal and an addition, so removals are overstated by an unknown amount. The right-hand end of the curve rests on the few links old enough to be measured there.

6. What the results change

Keep

  • Change-driven replay. It is the source of the 330× and it reproduces the direct method exactly.
  • The reverse index. 630× fewer resolutions, and replay cost that does not grow with the tree.
  • Facts cached by blob id. Small gain on one chain, 2.6× when every commit is indexed, and free re-runs. It costs one map.
  • One merged timeline. Cross-repository links came out dated with no special handling.
  • The from-scratch comparison as the main test. It is cheap to run on samples and it found a real mistake during this work (see limits).

Change

  • Drop anchors from the first version. Store intervals only and scan. Revisit past a few million intervals.
  • Stop saying the speed comes from content addressing. On a single chain it comes from only processing what changed. The earlier figure of 719× counted parses of source files only; the measured end-to-end gain is about 330×.
  • Make no claim about parallel extraction yet. Measure it on a quiet machine, with a real parser, before choosing a pool size.
  • Treat renames as lineage before reporting lifetimes. Exact-content matching is a start; edited moves need a similarity pass.

What this note adds. Resolved cross-file links with reference-counted lifetimes over a whole history, the reverse index applied to commit time, one timeline across repositories, and measurements of each part against the direct method. The contribution is the combination and the numbers. No single ingredient is new.

8. Limits

  • Extraction is a regular expression. It finds import specifiers and nothing else. It will miss computed imports and can match text inside strings or comments. A parser will be slower per byte. Every timing here is a lower bound on the real indexer's extraction time.
  • Resolution is simplified. Relative paths with the usual extensions and index files, and package names from package.json. No tsconfig paths, no exports maps, no workspace protocol. Links that depend on those are missing.
  • One language family. JavaScript and TypeScript only. Go, Python and PHP are not tested.
  • The correctness check shares code with what it checks. The from-scratch index uses the same extraction pattern and candidate rule. It proves the replay equals the direct method. It cannot catch a mistake both share.
  • An earlier version of the check was weaker than it looked. The first experiment compared the replayed links with links rebuilt from the replayed tree, so a wrong tree would have passed. The check now reads the tree from git independently.
  • Order across repositories rests on commit dates. Dates are made strictly increasing inside each repository, but a clock that was wrong on one machine can still place a commit early or late relative to another repository. A cross-repository link could then be dated by the wrong commit.
  • It depends on how git diffs merges. The walk asks for each merge to be diffed against its first parent. That option needs git 2.31 or later. On an older git the tree would drift without an error, which is the failure the file comparison in 5.4 exists to catch.
  • First-parent only. Work on a side branch appears at its merge, attributed to the merge commit. The author and date of the original change are not recovered.
  • Noisy timings. The machine was under load. Between-run spread on remotion was 3.1 s to 5.6 s. Ratios built from times carry that noise. Counts do not.
  • One large repository. Only remotion has a long history here. Nothing is known yet about histories ten or a hundred times longer.
  • The baseline total is extrapolated from 24 sampled commits.
  • Nothing is written to disk. No index format, no load time and no on-disk size were measured.

9. Reproduce

git clone https://github.com/ax3cubed/cartograph
git clone https://github.com/remotion-dev/remotion
cd remotion && git checkout 2b1b0c9 && cd ..

node cartograph/docs/research/bench.mjs remotion --runs 9   # one repository

The script needs Node 22 and git. It prints its results as JSON and stops with an error if any comparison fails. Run with no argument, it checks itself on a five-line hand-made history.
